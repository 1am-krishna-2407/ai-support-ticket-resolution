# Knowledge ingestion

```
manifest ──► fetch (SSRF-safe, robots.txt) ──► raw store ──► parse ──► skip if unchanged
                                                                   │
                     publish ◄── validate ◄── stage ◄── embed (reuse) ◄── chunk
```

Run it with:

```bash
docker compose run --rm backend python -m app.scripts.ingest            # everything
docker compose run --rm backend python -m app.scripts.ingest --only ci-variables
docker compose run --rm backend python -m app.scripts.ingest --force    # re-process all
```

The command prints a JSON summary and exits non-zero when the job fails.
(`make ingest ARGS="--force"` / `./tasks.ps1 ingest --force` are shortcuts.)

## 1. Manifest

`knowledge/manifest/sources.json` lists 217 GitLab docs pages across the 11 support
categories. It is generated by `knowledge/manifest/curate_manifest.py` from the published
English sitemap, so every URL exists. A priority list per category guarantees the pages
support tickets most often need (CI/CD variables, `.gitlab-ci.yml`, runner registration and
TLS, tokens, protected branches, webhooks, and so on); the rest are filled by path rules.
Entries are validated on load: https only, allowlisted host, known category, no duplicate
IDs or URLs. `retrieved_at` and `content_hash` are pipeline outputs and never appear in the
manifest. Set `"enabled": false` to hide a document from retrieval without deleting it.

## 2. Fetching (`services/ingestion/fetcher.py`)

- Syntax check: https, host in `ALLOWED_SOURCE_DOMAINS` (exact match), default port, no
  credentials, no IP literals.
- The host is resolved and rejected if **any** answer is loopback, private, link-local
  (including 169.254.169.254 metadata), CGNAT, multicast, reserved, or an IPv6 form wrapping
  one (IPv4-mapped, 6to4, Teredo, NAT64).
- The connection goes to the validated IP, with the real `Host` header and TLS SNI, so the
  certificate is still verified for the hostname and a second DNS lookup cannot redirect
  the request (DNS rebinding).
- Redirects are followed manually (max `FETCH_MAX_REDIRECTS`) and every hop is re-validated.
- robots.txt is loaded per host and enforced; an unreachable robots.txt disallows the host.
- Timeouts, a streamed size cap (`FETCH_MAX_RESPONSE_BYTES`), content types `text/html` and
  `text/markdown` only, retries with backoff and jitter on 429/5xx/network errors (honouring
  `Retry-After`), and one request per second per host.
- Raw bodies are stored content-addressed under `knowledge/raw/<document_id>/<sha256>.html`
  (git-ignored).

## 3. Parsing (`services/ingestion/parser.py`)

The GitLab parser takes `main .docs-content`, strips navigation, breadcrumbs, the table of
contents, code toolbars, feedback widgets, buttons, scripts, and images, and produces a tree
of blocks:

| Block | Source | Notes |
|---|---|---|
| `Heading` | `h2`–`h6` | keeps the anchor `id` for deep links |
| `Paragraph` | `p`, availability boxes | inline code kept in backticks; soft wraps collapsed |
| `ListBlock` | `ul`/`ol` | numbered procedures keep nested sub-steps and embedded code |
| `CodeBlock` | chroma `pre > code` | language from `data-lang` / `language-*`, exact whitespace |
| `TableBlock` | `table` | rendered as markdown |
| `Callout` | alerts, "History" collapsibles | label Note / Warning / Flag / History |

The document `content_hash` is computed from the extracted blocks, not the raw HTML (which
changes on every site build), so unchanged content is detected reliably. Parser output is
pinned by golden files built from real pages (`backend/tests/fixtures/`).

## 4. Chunking (`services/ingestion/chunker.py`)

- Chunks never cross a heading; each records its heading path (title › section ›
  subsection) and the anchor of its heading.
- Blocks are packed up to `CHUNK_TARGET_TOKENS` (450, measured with `tiktoken` o200k).
- Code blocks, lists, tables, and callouts are atomic. They are split only above
  `CHUNK_HARD_MAX_TOKENS` (900), at line, step, row, or sentence boundaries; tables repeat
  their header; such chunks are flagged `is_split_oversize`.
- Overlap (`CHUNK_OVERLAP_TOKENS`, 60) consists of whole trailing paragraphs only, never code
  or lists.
- `embedding_text` = heading path + content (so the embedding carries context); `content`
  stays readable for display and citation.
- `content_hash` = sha256 of `embedding_text`; `chunk_id` = sha256 of
  `document_id|version|index|content_hash`.

## 5. Embeddings (`providers/embeddings.py`)

Gemini `gemini-embedding-001` via `batchEmbedContents`, 1536 dimensions, `RETRIEVAL_DOCUMENT`
with the page title for chunks and `RETRIEVAL_QUERY` for queries. Vectors are L2-normalised,
and their count and dimension are validated. Requests are paced
(`EMBEDDING_MAX_REQUESTS_PER_MINUTE`) and retried on 408/429/5xx, honouring `Retry-After` or
Google's `RetryInfo.retryDelay`. Each retry is logged with the quota ID that was hit.

**Reuse:** before calling the provider, the pipeline looks up existing embeddings with the
same `content_hash` and the same embedding spec (`gemini-embedding-001@1536`). Unchanged
chunks in a new document version cost no API calls.

Every chunk must be at most 1800 tokens (o200k), well below Gemini's 2048-token input
limit, because batch requests cannot disable silent truncation.

## 6. Versioning and publish

| Step | What happens |
|---|---|
| Skip | active version has the same content hash **and** pipeline signature (parser version, chunk settings, tokenizer, embedding spec, manifest metadata) → nothing to do |
| Stage | new version N+1 inserted with status `staged`, together with all its chunks and embeddings, in one transaction |
| Validate | per staged document: chunks > 0, no missing embeddings, correct dimension, no empty chunks, hash recorded |
| Index | `ANALYZE document_chunks` (HNSW/GIN indexes update on insert) |
| Publish | one transaction: previous `active` → `superseded`, valid `staged` → `active` |

Retrieval only reads `active` + `enabled` documents. If the job crashes, its staged rows are
marked `failed`, and the previously active knowledge base stays exactly as it was.
Per-document failures (fetch, parse, embedding) are recorded in the job's `error_summary`
and do not stop other documents unless `--fail-fast` is given.

Only one ingestion runs at a time per database (Postgres advisory lock); a second run gets
`INGESTION_ALREADY_RUNNING`.

## 7. Job tracking

`ingestion_jobs` rows move through `running → validating → indexing → publishing →
completed | failed`. They hold counters (total, processed, changed, failed documents, chunks,
embedding calls, reused embeddings) and up to 200 error entries.

## 8. Provider quotas and interrupted runs

**Gemini free tier:** `EmbedContentRequestsPerDayPerProjectPerModel-FreeTier = 1000`, and
**every input in a batch counts as one request**. One day of free quota therefore embeds
about 1,000 chunks, while the full manifest is roughly 4,500. Query embeddings (every
search or ticket analysis) draw from the same daily budget. Gemini's 429 response for this
limit includes a misleading "retry in N seconds" hint, so:

- the provider recognises per-day quota IDs and raises `EmbeddingQuotaExhaustedError`
  immediately (no futile retries);
- ingestion then switches to **reuse-only mode**: it keeps fetching and parsing, publishes
  every document whose chunks all have stored embeddings, and **defers** the rest
  (`deferred_documents`) to a later run;
- the next run picks deferred documents up automatically, since they have no active version.

**Interrupted runs:** if a job is killed or cancelled, its row keeps its last stage. The
next run, while holding the lock, marks such jobs `failed` ("Interrupted") and their
staged documents `failed`. Their embeddings stay reusable, so nothing is paid for twice.

## 9. Real run results

**Final state (2026-09-30): 217 of 217 documents active, 4,600 chunks, every chunk embedded
with `Qwen/Qwen3-Embedding-0.6B@1024`.**

| Run | Provider / credit | Outcome |
|---|---|---|
| 1-3 (2026-09-29) | Gemini free tier | 45 documents; stopped by the 1,000-inputs-per-day cap. Exposed and fixed: fail fast on daily quotas, interrupted-job recovery, reuse-only mode. Vectors later cleared by migration 0005 when switching models |
| Qwen 1-2 | Hugging Face account 1 | 24 documents before "monthly included credits depleted" |
| Qwen 3 | Hugging Face account 2 | +16 documents |
| Qwen 4 | Hugging Face account 3 | +99 documents (2,739 chunks), including re-embedding the cleared Gemini-era documents |
| Qwen 5 | Hugging Face account 4 | +10 documents, plus one page GitLab had updated (a new version, reusing its unchanged chunk embeddings) |
| Qwen 6 | Hugging Face account 5 | +68 documents (915 chunks, 101 calls); corpus complete, 0 deferred |
| Verification | none needed | **217 unchanged, 0 changed, 0 embedding calls, 0 failures** (218 s, just fetch and parse) |

Every run stopped cleanly when credit ran out: embedded documents were published, the rest
deferred and picked up by the next run with no repeated work.

**Cost note.** A Hugging Face free account's monthly Inference Providers credit covered
roughly 400-2,700 chunks here, depending on what else the account had used. The full corpus
is about 4,600 chunks, and re-embedding it (for a model or chunking change) needs a paid
credit balance or a locally run model. Every search also spends one query embedding.
